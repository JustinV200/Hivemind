## Deliverables

2. **The Hive-state floor (ADR-0033).** `GuardPolicy` gains the Hive's state paths (the resolved `[hive] db` and its `-wal`/`-shm` siblings, the resolved `[hive] secrets_dir` and everything under it, the manifest file itself), set by the composition roots from the manifest; for every bee principal (Warden and Worker) the floor refuses `fs:read`/`fs:write` needing any of them, `exec` of `hive` or `hivemind-*` (match the basename of argv[0], so `/x/.venv/bin/hive` is caught), and `net` to a loopback name or address (`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`, `0.0.0.0/8`, `::`, IPv4-mapped forms) or one of the Hive Stand's own addresses. Because a capability string can spell a loopback host many ways (`127.1`, `2130706433`, a DNS name resolving to 127.0.0.1), **also** harden the HTTP tool (`workers/tools/http.py`): resolve the host, refuse (as a `guard.denied` through the Enforcer, rule `guard.state_floor.loopback`) if any resolved address is loopback, unspecified, link-local, an IPv4-mapped form of those, or one of the Hive Stand's addresses, and pin the request to the checked address with the name kept in `Host` and TLS SNI (`httpx` request extension `sni_hostname`), exactly as `hivemind/entrance/push/destinations.py` already does for webhooks — reuse its approach (not its module: `workers` may not import `entrance`; if a shared helper is warranted, put it where both layers may import it, e.g. `hivemind.guard`).
3. **Night Veil floors (10.3a).** When the context's bound or requested tier is `NIGHT_VEIL`: placement never uses a Real Cell (refuse `cell:hive_stand` and `cell:real:*` needs; `cell:virtual` must be held); every slot binding (first binding, rebind, grant's allowed bindings) must be local (a provider whose base URL is loopback or which runs in process), else refused; Honey is allowed at `c0`/`c1` and refused at `c2` (the HONEY_ACCESS point is pending until phase 7 — the floor exists and is tested through `evaluate`); the location families (`geo`, `wifi:scan`, `host:metadata`) are refused. The control-channel floor: a Night Veil Cell's Waggle endpoint (the `QueenEndpoint` built for it at provisioning) must dial a `.onion` host through the configured Tor SOCKS proxy, never the VPN interface or a clearnet address; wire it at the provisioning site. Also fix the phase 5 gap the audit found: the production composition root never builds `PlacementPolicy.night_veil`, so every Night Veil task fails placement — build it from `[security.tiers.NIGHT_VEIL]` (and refuse loudly, at the moment a Night Veil goal is placed, when the tier profile lacks its hidden-service address or SOCKS proxy).
4. **Tier inheritance (10.3b).** Dispatch binds a task to its Cell's `CombShieldLevel` (persist it on the task in the Brood Chamber with its assignment, e.g. `Task.bound_tier`, and carry it in `PolicyContext.bound_tier` at every later check for that task: slot rebinding, grant revision, egress changes); a task unassigned and re-dispatched (Warden lost) is re-bound at its next placement before it runs again. Tests: a task bound to NIGHT_VEIL cannot be rebound to a hosted slot; a task moved between Cells of different tiers is re-bound before resume.
5. **Initiation (10.3c).** Night Veil placement requires the task's origin `HUMAN` **and** a goal request id on the task whose request asked for `NIGHT_VEIL` explicitly (ADR-0031: only a structured goal request initiates it; a chat message never does); the Queen or a Warden can never produce it.
