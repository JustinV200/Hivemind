## Deliverables
1. **Durable goal requests (`queen/intake/` package).** `GoalRequest` (frozen): id (a hivemind-local `GoalRequestId` NewType minted as a prefixed ULID with the injected clock), text (bounded like a goal), budget USD (optional; the goal's own spend cap, never above `[forage] spend_cap_per_goal_usd`), requested Comb Shield tier (optional), clearance, origin (`RequestOrigin.HUMAN` for the Entrance), device id (optional; None for the local CLI), the goal's capability ceiling as strings (optional), source (`typed` or `spoken`), state, goal id once planned, a refusal reason, timestamps. States and one transition table (`RECEIVED → PLANNING → PLANNED | REFUSED`; `RECEIVED → AWAITING_CONFIRMATION → RECEIVED | REFUSED`; `PLANNING → REFUSED`) with a comment per edge; add the row to codingrules Appendix C. A `GoalRequestStore` protocol, SQLite (own migration series `queen_intake`) and in-memory implementations, one contract suite. **The Queen owns planning:** `Queen.request_goal(request) -> GoalRequestId` commits the row and sets a wake signal; a new tick delegate drains `RECEIVED` rows (`PLANNING`, then `submit_goal` with the request's budget, tier, origin, device, ceiling and request id, then `PLANNED` with the goal id, or `REFUSED` with the reason); `confirm_goal_request(id)` moves `AWAITING_CONFIRMATION → RECEIVED`; on start, a `PLANNING` row whose root task already exists in the chamber (find it by the request id carried on the task — add a `goal_request_id` to `TaskSpec` if step 10.3 did not) becomes `PLANNED`, otherwise it is planned again, so a crash after the Entrance's `202` loses nothing and never double-plans. A goal whose request names a tier must carry it into its tasks' needs and its request id into the task's origin fields, which is what the Night Veil floor reads.
2. **The wake signal.** The Queen awaits an in-process wake event beside her Warden links in `_run_tick`, so a goal request or a human message wakes her at once instead of waiting for the next heartbeat. `queen.py` is at 300 lines of code: move logic out into delegate modules (`queen/ticks/…`) rather than growing it, and keep it under the limit.
3. **The chat log (`queen/chat/` package).** One append-only log (`C2`): each entry has an id, time, author (`human` or `queen`), kind (`message`, `reply`, `question`, `alarm`, `notice`), text (bounded; for a question or Alarm the text the human must read), a ref (question id, Alarm id, goal request id), the device id for a human entry, and `handled_at` for human messages. Protocol + SQLite (own series `queen_chat`) + in-memory, a contract suite, and reads by time/cursor for the Entrance's `/v1/chat` and its stream.
4. **Human messages into the inbox.** `Queen.post_human_message(text, device_id, task_id=None) -> chat entry id`: appends a `human`/`message` entry and wakes her; the tick drains unhandled human entries into `InboxItem(kind=HUMAN_MESSAGE, principal="human", payload=<wire HumanMessage>)` so the Attendant scores it (`WeightTable.queen_default()` already weighs `HUMAN_MESSAGE`); autopilot has no rule for free text (`NEEDS_JUDGEMENT`); the awake episode's trigger carries the message text as a delimited, labelled section (it is the human's own text but may come from a compromised device: label it as such; the scanner of step 10.6b will run on it later — leave a clearly named hook); the entry is marked handled once the decision is written.
5. **The `REPLY` action.** `QueenAction.REPLY` and a bounded `message` field on `QueenDecision` (required for REPLY, refused otherwise); the awake decision schema and prompt offer it; `_act`'s REPLY appends a `queen`/`reply` chat entry. Every autopilot/awake table that maps actions gains the row (a missing mapping must be a test failure, not a runtime KeyError).
6. **Questions and Alarms reach the chat.** When the Queen routes a question to the human, append a `queen`/`question` entry (ref = question id); when an Alarm escalates to the human, a `queen`/`alarm` entry (ref = Alarm id). Add `Queen.acknowledge_alarm(alarm_id)` which resolves it in `HumanInbox` (nothing calls `resolve` today).
7. **The `HumanChannel` seam.** A Protocol in `queen/` with a documented no-op default, injected through `QueenDeps`, called on: a reply, a question for the human, a question answered or withdrawn, an Alarm that reached the human, an Alarm acknowledged, a goal request refused or planned, a goal whose tasks are all terminal (with its request). The Entrance implements it in a later step to push notices; the Queen never imports the Entrance.
8. **Trail events** (never text): a goal request received/refused, a human message arrived, the Queen replied. `hivemind/pheromone/events/families.py` is at 299 of 300 lines of code: first turn it into a package (`pheromone/events/families/`, codingrules 5.2) with the same public names, then add the kinds to the `queen` family and document them in the vocabulary.
9. Keep `hive run` and `hive tasks submit` working exactly as today (they call `submit_goal` directly, with no request row), and every existing test green.
10. Tests: a request survives a simulated crash in each state and is planned exactly once; confirmation; a human message wakes the Queen without any Warden traffic, reaches an awake episode whose assembled prompt contains the message (use `FakeLLMProvider` returning a REPLY decision) and produces a reply entry; questions and Alarms appear in the chat; the in-process answer path saves the keep-for-goal choice; `HumanChannel` receives every call.
